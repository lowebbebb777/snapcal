One job, end to end

何が起きるか

画像の読み込みから予定登録まで、緑の枠内はすべてスマホの中。外部AIへスクショを渡さない。

この端末の中だけ
01 / INPUT

スクショを受け取る

自動検出、または共有メニューから1枚だけ。

02 / READ

日本語OCR

APK同梱モデルが文字と位置をメモリ上で読む。

03 / JUDGE

安全ゲート

未来・一意・除外語なし・重複なしを決定的に判定。

04 / WRITE

カレンダー追加

CalendarContractで選択済みカレンダーへ登録。

05 / CONTROL

通知とUndo

結果だけを表示。アプリが作った予定だけ取り消せる。

×外へ出さない: スクショ、OCR全文、予定名、場所、URL。INTERNET権限・OpenAI・バックエンド・APIキーも持たない。
Two inputs, one brain

入口は2通り

理想はLINE横のような常駐型A。Android制約や権限で不安定なら、同じ解析部分を使う共有型Bでデモを守る。

画像を共有 → その場で処理

GalleryやLINEからSnapCalへ共有。広い写真権限と常駐を使わない。

SAFE FALLBACK

2SnapCalを選択

4URI参照を即破棄
全写真アクセスなしオーバーレイなしForeground ServiceなしCalendar
Fail closed

勝手に誤登録させない

OCRが読めたことと、予定を登録してよいことは別。すべての条件が揃った場合だけ自動登録する。

自動登録の必須条件

✓イベントが1件だけ
✓タイトルが一意
✓日付＋開始時刻の根拠あり
✓未来400日以内
✓営業時間・期限ではない
✓同じ画像・予定が未登録
✓24時間以内の予定
✓形式・長さ制約を通過

分岐

全部OK → 自動追加

30分前通知を付け、完了通知とUndoを表示。

1つでも不明 → 追加しない

曖昧、過去、営業時間、複数予定は安全側で停止。候補本文も保存しない。

Data minimization

残すもの／消すもの

処理に必要な内容はメモリだけ。Roomには復元できないハッシュとCalendar操作メタデータだけを30日間残す。

Build order · 22h + 2h reserve

実装する順番

見た目から作らず、Android固有の不確実性とCalendar副作用を先に潰す。各節目でfallback判断を固定する。

M0 · 0–4h

成立性を証明

SDK、空APK、実機、Calendar、共有取込、監視とoverlayの短いスパイク。

4hで不安定ならBを主経路へ
M1 · 4–9h

Fake OCR縦切り

取込→重複排除→Calendar→通知→Undo→クラッシュ回復を通す。

安全なADD/DELETE照合は削らない
M2 · 9–14h

実OCRを接続

日本語モデル、画像縮小、日時・タイトル抽出、除外語を接続。

精度不足なら受理書式を絞る
M3 · 14–18h

権限と障害処理

FGS、バブル、権限取消、24h stale、30日cleanupを固める。

overlay不安定ならBへ固定
M4 · 18–22h

評価とデモ

正例8・負例6、オフライン、p95、UI、release APK、30秒デモ。

20hで機能凍結、残りは回帰
